We'll use this project for a hands-on exercise. The key learning objective is to maintain a small flake repository while developing and testing the package, then move the package expression into nixpkgs using its own conventions.

## 1. The workflow you will learn

Upstream PDFCraft releases

AppImage, Debian package, version, checksum

Your GitHub flake repository

flake.nix + packages/pdfcraft.nix + lock file

Build and test on NixOS

Evaluate, build, launch, check GUI and dependencies

Nixpkgs pull request

Package under pkgs/by-name, tests and review

One important distinction: the flake is a development and distribution interface. The package derivation is the part that nixpkgs ultimately needs. A nixpkgs submission normally does not require adding your personal `flake.nix`.

## 3. Create your own flake repository

For the first iteration, use a separate repository such as `pdfcraft-nix`. This lets you experiment without changing the upstream project or nixpkgs.

On your NixOS machine:

```
mkdir -p ~/projects/pdfcraft-nix/packages
cd ~/projects/pdfcraft-nix

git init
```

Your initial directory structure will be:

```
pdfcraft-nix/
├── flake.nix
├── flake.lock          # Generated by Nix
├── README.md
└── packages/
    └── pdfcraft.nix
```

### Step 1: Write the package expression

Create `packages/pdfcraft.nix`:

```
{
  lib,
  appimageTools,
  fetchurl,
}:

let
  pname = "pdfcraft";
  version = "2026.10.09-a300702";

  # Obtain this URL from the actual GitHub release asset.
  src = fetchurl {
    url = "REPLACE_WITH_OFFICIAL_APPIMAGE_URL";

    # Replace this placeholder with the verified SHA-256 hash.
    hash = lib.fakeHash;
  };
in
appimageTools.wrapType2 {
  inherit pname version src;

  # The AppImage contains its own application files.
  # Add extra runtime libraries here only if required.
  extraPkgs = pkgs: [ ];

  meta = {
    description = "PDFCraft desktop application";
    homepage = "https://github.com/PDFCraftTool/pdfcraft";
    license = lib.licenses.agpl3Only;
    platforms = [ "x86_64-linux" ];
    mainProgram = "pdfcraft";
  };
}
```

The URL and hash are deliberately placeholders. Do not attempt to publish this version until you replace them with verified values and confirm the actual executable name.

What the expression teaches:

- `let ... in` defines local variables such as `pname`, `version`, and `src`.
- `{ lib, appimageTools, fetchurl }: ...` is a function receiving dependencies from Nix.
- `fetchurl` downloads a fixed artifact and verifies its hash.
- `appimageTools.wrapType2` adapts an AppImage to the Nix store.
- `meta` describes the package for users and package-search tools.

### Step 2: Find the actual AppImage URL

Use GitHub's release API to retrieve the exact asset URL instead of guessing its filename:

```
# List the AppImage assets attached to this release.
curl -fsSL \
  https://api.github.com/repos/PDFCraftTool/pdfcraft/releases/tags/v2026.10.09-a300702 \
  | jq -r '.assets[]
    | select(.name | endswith(".AppImage"))
    | [.name, .browser_download_url] | @tsv'
```

If the command returns an AppImage, copy its `browser_download_url` into the derivation. If there is no matching asset, inspect the returned asset list and release page for the actual filename.

Then prefetch the file to obtain its hash:

```
nix store prefetch-file --json \
  "PASTE_THE_VERIFIED_APPIMAGE_URL_HERE"
```

Use the resulting SHA-256 SRI hash in `hash`. If the upstream project publishes a checksum file, verify the downloaded artifact against it as well.

### Step 3: Export the package from your flake

Create `flake.nix`:

```
{
  description = "A Nix flake for PDFCraft";

  inputs = {
    # Pin the Nix package collection used to build PDFCraft.
    nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";
  };

  outputs = { self, nixpkgs }:
    let
      # Start with the common 64-bit Intel/AMD Linux architecture.
      system = "x86_64-linux";

      # Import nixpkgs for this architecture.
      pkgs = import nixpkgs { inherit system; };

      # Evaluate the package expression with its dependencies.
      pdfcraft = pkgs.callPackage ./packages/pdfcraft.nix { };
    in
    {
      # Export the package under a named attribute.
      packages.${system} = {
        inherit pdfcraft;

        # Makes `nix build` select PDFCraft by default.
        default = pdfcraft;
      };
    };
}
```

Here, `inputs` declares dependencies of the flake. `outputs` defines what the flake provides. `callPackage` evaluates your package function and supplies dependencies from `pkgs`.

The `flake.lock` file is generated by Nix and records the resolved input revisions. It is important to commit this file to make your development environment reproducible.

## 4. Evaluate and build the flake

First, generate the lock file and check the flake:

```
nix flake lock
nix flake check
```

Build the application:

```
nix build .#pdfcraft
```

During the first build, Nix may report a hash mismatch because `lib.fakeHash` is still present. Replace it with the reported hash, then rebuild.

After a successful build:

```
ls -l result/bin
```

Inspect the executable name rather than assuming it matches the package attribute. Then launch it from a graphical NixOS session and test its PDF operations.

## 5. Understand how this differs from the upstream flake

PDFCraft's existing flake uses a different approach: it calls `./nix/package.nix`, exports an overlay, and provides NixOS and Home Manager modules. Its package expression builds a static web application and wraps it with Nginx rather than simply wrapping the downloadable AppImage.&#x20;

This illustrates an important packaging choice:

| Approach                | What you learn                                              | Main trade-off                                                 |
| ----------------------- | ----------------------------------------------------------- | -------------------------------------------------------------- |
| AppImage wrapper        | Binary packaging, hashes, runtime compatibility             | Depends on upstream's prebuilt artifact                        |
| Build from source       | Build phases, dependencies, reproducibility                 | More complex, particularly for Node.js and native dependencies |
| Upstream Nix expression | Flakes, overlays, modules, application-specific build logic | Requires understanding and testing the existing build          |

For a nixpkgs submission, compare your work against the upstream Nix expression first. You may find that the existing source-based approach is more appropriate than wrapping the AppImage, but that must be established through successful builds and tests.

## 6. Prepare the package for nixpkgs

The official nixpkgs repository uses a `pkgs/by-name` directory structure for new packages. The contribution guide also emphasizes package necessity, source verification, testing, metadata, and maintainability.&#x20;

Your final nixpkgs change should look approximately like this:

```
nixpkgs/
└── pkgs/
    └── by-name/
        └── pd/
            └── pdfcraft/
                └── package.nix
```

Before submitting, verify that the package name is not already present in nixpkgs. Then:

1. Fork `NixOS/nixpkgs` on GitHub.
2. Clone your fork and add the official repository as `upstream`.
3. Create a branch based on the current target branch.
4. Add the package in the appropriate `pkgs/by-name` directory.
5. Build and test it using nixpkgs conventions.
6. Commit and push your changes.
7. Open a pull request against `NixOS/nixpkgs`.

Example setup:

```
git clone https://github.com/YOUR_USERNAME/nixpkgs.git
cd nixpkgs

git remote add upstream https://github.com/NixOS/nixpkgs.git
git fetch upstream

# Use the base branch specified by the current contribution guide.
git switch --create add-pdfcraft upstream/master
```

After adding the package:

```
# Evaluate and build the package using nixpkgs.
nix build .#pdfcraft

# Review your changes before committing.
git diff --check
git diff
```

The package must be registered correctly in the nixpkgs package set for `.#pdfcraft` to work. Follow the current [nixpkgs package contribution guide](https://github.com/NixOS/nixpkgs/blob/master/pkgs/README.md) for the exact checks and conventions.

## 7. Publish your development flake separately

Once your own flake builds and launches correctly, commit the repository and push it to GitHub:

```
git add flake.nix flake.lock packages README.md
git commit -m "Add PDFCraft Nix flake"

git remote add origin \
  https://github.com/YOUR_USERNAME/pdfcraft-nix.git

git branch -M main
git push -u origin main
```

Other users can then test your package using:

```
nix run github:YOUR_USERNAME/pdfcraft-nix#pdfcraft
```

Replace `YOUR_USERNAME` with your actual GitHub username. This is the independent distribution route; the nixpkgs pull request is the separate route for inclusion in the official package collection.

One final point: because you are using AI assistance to develop the contribution, review and understand every change before submission. The current nixpkgs policy requires disclosure of non-trivial AI-assisted contributions using the prescribed `Assisted-by:` Git commit trailer.
